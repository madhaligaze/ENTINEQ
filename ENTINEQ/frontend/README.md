# ENTINEQ / frontend

**Фронтенд публичного приложения ENTINEQ (powered by Claude).** Маленький сервис на Node: отдаёт страницы (вход, регистрация по приглашению, чат, индикатор лимита с таймером; тёмная и светлая тема, работает на телефоне) и пересылает запросы `/api/*` и чат `/ws` на [backend](../backend) по адресу из переменной `BACKEND_URL`. Своих данных и секретов у него нет.

```
браузер ──https──▶ этот сервис ──/api, /ws──▶ backend ENTINEQ ──▶ backend ENTINEQ_AGENT ──▶ Claude
         страницы
```

**Зачем пересылка, а не обращение браузера напрямую к бэкенду.** У браузера один адрес на приложение: cookie входа остаются «своими» (сторонние cookie режут Safari и другие), работает защита от CSRF, а бэкенд можно вообще не публиковать в интернет (достаточно внутренней сети Railway).

## Что делает сервис

- **Страницы** из `public/` (HTML, CSS, ES-модули без сборки) со строгой политикой безопасности (CSP без инлайн-скриптов; текст сообщений выводится только как текст - XSS невозможен), `no-cache` с проверкой по ETag - после обновления не остаётся старого интерфейса.
- **Пересылка `/api/*`.** Передаются только нужные заголовки (cookie, Origin и т.п.); чужие `Authorization`, `X-User-Token` и `X-Forwarded-*` отбрасываются, а настоящий IP посетителя и адрес сайта добавляются заново. Ответы не кэшируются, `Set-Cookie` доходит целиком. Принимается только JSON (до 100 КБ).
- **Пересылка `/ws`.** Кадры идут в обе стороны как есть; сообщения, пришедшие раньше, чем установилось соединение с бэкендом, ждут в очереди. Код закрытия `4401` («нужно войти») доходит до браузера без изменений.
- **Основной предел частоты** попыток входа/регистрации и открытий чата - по настоящему IP посетителя (10 и 30 в минуту; настраивается).
- **Сбои бэкенда:** спокойное `502` с понятным текстом (подробности - только в логах); страницы продолжают открываться, чат сам переподключается, как только бэкенд вернётся.
- **Строгая проверка пути.** Адреса с точечными сегментами (`..`, `%2e%2e`), двойным слешем, обратными или закодированными слешами и нулевым байтом отклоняются у фронтенда и до бэкенда не доходят. Проверка не зависит от того, отсекает ли такие адреса сам веб-фреймворк.
- Ничего, кроме `/api/*`, `/ws` и страниц, на бэкенд не пересылается.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `BACKEND_URL` | да | Адрес бэкенда ENTINEQ: только сервис, без пути. В production - `https://` (исключения: `*.railway.internal`, `localhost`, имена без точки). |
| `PORT` | нет | Railway задаёт сам. Локально - 3001. |
| `TRUST_PROXY_HOPS` | нет | Сколько прокси стоит перед сервисом. В Railway - один (по умолчанию `1`), локально `0`. |
| `RATE_LIMIT_AUTH_PER_MIN`, `RATE_LIMIT_WS_PER_MIN` | нет | Пределы частоты (10 и 30). |
| `BACKEND_TIMEOUT_MS` | нет | Сколько ждать бэкенд на обычный запрос (30 000). |

Остальное - в [`.env.example`](.env.example). При ошибке в конфигурации сервис сразу пишет понятную причину и не стартует.

## Запуск локально

```bash
pnpm install
cp .env.example .env     # BACKEND_URL=http://localhost:8081
pnpm dev                 # http://localhost:3001
```

Запущены должны быть бэкенд ENTINEQ ([backend](../backend), порт 8081) и бэкенд ENTINEQ_AGENT. В `.env` бэкенда ENTINEQ в `ALLOWED_ORIGINS` - адрес этого сервиса (`http://localhost:3001`).

## Проверка

```bash
pnpm typecheck
pnpm test        # 49 тестов с поддельным бэкендом, записывающим всё, что до него дошло
```

## Деплой в Railway

1. Залейте содержимое этой папки в отдельный репозиторий GitHub.
2. Railway → в том же проекте, что и бэкенды: **+ New → GitHub Repo**. Сборка по `Dockerfile`, проверка здоровья `/healthz` - из `railway.json`.
3. **Variables:** `BACKEND_URL` = `http://${{entineq-backend.RAILWAY_PRIVATE_DOMAIN}}:${{entineq-backend.PORT}}`.
4. **Settings → Networking → Generate Domain** (или свой домен). Этот адрес впишите в `ALLOWED_ORIGINS` бэкенда ENTINEQ: `https://<домен>`.
5. Откройте `https://<домен>/readyz` - `{"ok":true}` значит, что бэкенд виден. Связку «бэкенд ENTINEQ → ядро» показывает `/readyz` самого бэкенда.

`/healthz` - только «сервис жив» (по нему Railway принимает деплой), `/readyz` - ещё и «бэкенд отвечает».

## Оформление

Интерфейс следует правилам из `CLAUDE.md` в корне проекта: монохром с волосяными рамками; цвет только для отказа (красный), никакого «всё хорошо» зелёным и цветных точек у состояний; кнопки и поля без скруглений (главное действие - сплошная плита, остальное - рамка); выбранное показывается весом подписи и чертой; тема по системе (тёмная и светлая). Соблюдение проверяет `e2e/ui-style.e2e.cjs` по вычисленным стилям на ширинах 1440, 800 и 390 в обеих темах.

## Структура

```
src/
  server.ts      запуск
  app.ts         сборка Fastify: страницы, пересылка /api, заголовки безопасности, пределы частоты
  ws-proxy.ts    прокладка WebSocket
  path.ts        проверка пути до пересылки на бэкенд
  config.ts      переменные окружения с проверкой (Zod)
  listen.ts      прослушивание на всех интерфейсах (IPv6 и IPv4; приватная сеть Railway)
public/          веб-интерфейс (HTML, CSS, ES-модули без сборки)
test/            тесты
```

Модули `public/js/{api,dom,format,usage,chat}.js` совпадают с фронтендом [ENTINEQ_AGENT](../../ENTINEQ_AGENT/frontend) (интерфейс чата у них общий), как и весь код в `src/` и `test/`. Правите в одном - перенесите в другой.

Здесь же - место для «продуманного UI/UX»: можно заменить простые страницы на React/Vite - собранные файлы отдавайте из `public/`, сервис пересылки не меняется.
